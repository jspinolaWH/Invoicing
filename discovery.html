52 Requirements.
One AI. A Working Product.

This is the story of how we built a complex invoicing system using AI as the primary builder. We started with a list of 52 written requirements — and ended with a working, verified product where 49 of 52 features were confirmed automatically, without a developer checking them by hand.

We'll also walk through how our team plans and estimates features together — the process that makes it possible for AI to build the right things in the first place.

01
Chapter 1
The Starting Point

Before a single line of code was written, the product team had documented everything the invoicing system needed to do. These are called requirements — one written statement per feature, describing exactly what the system must be able to do and under what conditions. Think of them as a contract between the business and the development team. Here are a few examples of what a real requirement looks like.

Example requirements — plain English statements of what the system must do
Requirement · Billing
"Users must be able to filter the invoice list by status: Draft, Sent, or Paid."
This means a filter button must appear on the screen and actually work — not just exist in the code somewhere.
Requirement · Price Lists
"A price list must support multiple currencies and apply the correct rate automatically based on the customer's country."
This touches data, business rules, and what the user sees — three different parts of the system working together.
Requirement · Invoice Generation
"The system must prevent duplicate invoices from being created for the same customer and billing period."
A rule that lives in the background — the user never sees it, but it must be there and it must be tested.
Requirement · Seasonal Fees
"Seasonal fees must be automatically applied to matching services within a billing cycle, without manual input from the user."
Automation — the system does the work so the person using it doesn't have to remember every rule.
We had 52 of these. Each one describing a single behaviour the system must have. Some were simple. Some had hidden complexity. A few depended on other requirements being built first. The challenge: how do you turn 52 of these into working software — reliably, quickly, and without missing anything?

Chapter 2
How AI Built It

Instead of handing all 52 requirements to developers and waiting weeks, we gave them to an AI. The AI read every requirement, figured out what depended on what, created a step-by-step build plan — and then built, checked, and fixed each feature in sequence. Two specialised AI agents, Ralph and Ralph-Brother, made sure nothing slipped through. Here is exactly what happened.

Chapter 3
Meet Ralph & Ralph-Brother

Two AI agents. Each one asking a completely different question. This is what makes the process robust — one checks that the feature exists in the code, the other checks that a real user can actually find and use it on screen. You need both. The example below shows exactly why.

Ralph & Ralph-Brother  ·  Two Checks, Two Different Questions
They run at the same time because they look at completely different things and never interfere with each other.
Ralph  ·  "Is the feature actually built?"
✓ Reads every requirement and checks whether the code for it exists
✓ Finds missing features, business rules, and data storage
✓ Writes a list of what's missing, then builds it
✓ Re-checks every fix immediately to confirm it worked
✗ Never opens the app. Does not check if users can actually see the feature.
Ralph-Brother  ·  "Can a real user actually find it?"
✓ Knows which features are already visible to users and which aren't
✓ Checks the underlying code first, before touching anything on screen
✓ Fixes both the hidden logic and the visible screen in one pass — buttons, pages, connections
✓ Re-tests every fix: follows the exact steps a real user would take
✓ A feature only passes when a user can find it, click it, and use it on screen

Chapter 4
The Planning Process

By the time this process starts, an AI mockup already exists. The team doesn't read requirements in the abstract — they read them while looking at the screen. That changes everything. A requirement that sounds vague on paper becomes obvious the moment you can point at it and ask "is this what we mean?" The mockup is the shared reference that makes the conversation concrete before any real code is committed.

Feature Planning  ·  Four Steps, Every Time
This process happens after an AI mockup is already in place. The team reads each task and matches it against what they can see on screen — using the mockup as a visual reference to validate, challenge, and sharpen the requirements before committing to building them for real.

What happens in each step
STEP 01
Grooming
The team reads each task while looking at the AI mockup on screen. The question is not "how do we build this?" — it's "does what we wrote match what we're looking at?"

The mockup makes vague requirements concrete. It turns a sentence on a page into a real screen you can point at, question, and validate.

If something doesn't line up — the requirement says one thing, the screen suggests another — that gets resolved before any real code is written.
The mockup is the shared reference — it replaces a hundred words of description
STEP 02
Task Breakdown
Split the feature into small, individually completable tasks. Separate by layer: what the user sees · the logic behind it · automated tests

Each task has a clear done condition. There is no "80% done" — a task is either done or it isn't.

Make dependencies explicit so the team works in the right order.
If you can't estimate it confidently, it's still too big — break it further
STEP 03
Shared Blueprint
Before any code is written, both sides of the team agree on the exact shape of the data they will exchange. Like an architect's drawing — both sides agree on where the walls go before construction starts.

With a blueprint: both sides build at the same time, independently. Without one: the day you thought you were finished becomes a debugging session.
~30 minutes to write · hours saved when connecting the pieces
STEP 04
Estimation
The team scores how complex the task is — not how many hours it will take. This happens after the blueprint is written, because the blueprint removes hidden unknowns that make estimates unreliable.

A big disagreement between team members is valuable information, not a problem. It means someone sees something the others don't. Stop and talk about it.
Estimate after the blueprint, not before
05
Chapter 5
Estimating Complexity

We don't estimate in hours — we estimate in complexity points. Hours are unreliable because they depend on who does the work and what surprises come up. Complexity is about how well-understood the problem is, how many moving parts it has, and how likely it is to hit an unexpected edge case. Five points on the scale below. One rule: if you reach 8, it's not a task yet.

Complexity scale — what each number means
1
Done this exact thing before. Zero unknowns. Very low risk.
2
Similar to things I know well. Small edge cases possible.
3
Understood, but has several moving parts. Some coordination needed.
5
More complex. Real unknowns. Could hit an unexpected edge case.
8
Still too big. Too many unknowns — split it before estimating.
